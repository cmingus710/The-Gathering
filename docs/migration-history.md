## Evidence that the schema matches the committed migrations

`supabase/tests/schema-fingerprint.sql` is a read-only query that digests the schema by category:

- enums, columns, constraints, indexes, RLS flags
- policies (public and `storage.objects`)
- function signatures, security/`search_path`, and comment- and whitespace-normalized bodies
- function and table/column grants for `anon`, `authenticated`, and `service_role`
- triggers, comments, buckets, and seeded catalog rows

It was run against:

- **(A)** the hosted project
- **(B)** a fresh PostgreSQL 16 database built from `supabase/tests/supabase-shim.sql` plus every committed migration

## History repair

The equivalent of `supabase migration repair` was done in two steps. Only rows in `supabase_migrations.schema_migrations` change; no schema or application data is touched.

1. **Done:** the five repository versions were marked applied (`20261018000100`–`20261018000500`, `created_by = 'migration-repair'`).
2. **Done (owner, SQL editor):** the ten connector versions were marked reverted (rows removed):

   ```sql
   delete from supabase_migrations.schema_migrations
   where version in ('20261018204248','20261018204304','20261018204444','20261018204620','20261018204746',
                     '20261018204755','20261018204811','20261018204824','20261018204829','20261018204842');
   ```

**Verified 2026-10-18:** `list_migrations` on the hosted project returns exactly the five repository versions:

```
20261018000100 identity_and_capabilities
20261018000200 church_settings
20261018000300 announcements
20261018000400 storage
20261018000500 explicit_function_grants
```

The remote history and `supabase/migrations/` now agree, so `supabase db push` and `supabase migration list` can be used normally.

## Going forward

Apply new migrations with `supabase db push` (or the SQL editor followed by `supabase migration repair --status applied <version>`). Don't apply schema through the connector's `apply_migration`, because it records its own version numbers.
